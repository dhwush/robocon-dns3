## 明确证据

00:05诊断左上为“2号 原图：本帧=蓝，锁定=2”。下方RGB顶块“合格1个；唯一候选通过”，顶块状态“已确认”，归属C2→2号。红蓝约3486/3531px，红蓝上下关系通过。可见近处顶块蓝在上、红在下，当前读色正确。原帧见`diagnostic_005.jpg`。

00:10及00:20主窗口却把该塔标成紫色“两层”，右侧显示“2号 两层 已确认”。该标记没有识别方法后缀，也与显示代码在本帧结果和锁定值不一致时隐藏方法的行为吻合。

`survey_20261117_125215.json`记录起点x=−2.515、y=0.024、yaw=−45°，2号在本轮elapsed_s=4.4943时已被确认成`2`，后续pending中已移除。4.49秒是事件发生时刻，不代表连续稳定观察4.49秒。

## 原因链

1. 自主确认路径`autonomous.py`在满足可见、稳定、偏好等门槛后，直接将当帧`view.conclusion`写入`vote.locked`。因此某次短暂只读到白盒两层的结果可以成为整塔最终结果。
2. 同一文件对已锁定目标直接清空证据并continue，还将recheck置False；不会检查后续明确蓝顶与旧两层之间的矛盾。
3. `report.py`启用autonomy后直接返回，后面的`vote.see()`冲突累计逻辑不会执行。不能指望Vote的15帧异议机制修正自主模式结果。
4. `view_field.py::live_panels`及`paint_window`都优先显示locked，导致真实蓝顶轮廓被配上旧“两层”标签和紫色。

因此，本次录像明确显示的主要故障是“早先层数结果被永久锁定，后来正确顶色无法纠正”，而非当前RGB持续把蓝色认错、或顶块归属到了别塔。

## 证据边界与处理方向

确认事件发生于本段录像之前，没有当时原始RGB-D，无法断言首次输出两层是深度缺测、姿态变化、遮挡还是其他原因。当前录像能证明其后正确蓝顶被旧状态压住；不应把82.5/101cm等不同帧深度值直接解释为当前“两层”来源。

修复应优先处理确认及展示：白盒层数确认需要稳定证据；已锁定层数后遇到可靠同塔顶块证据，应累计冲突并复核；本帧蓝顶与已确认两层应分别显示。不能只改HSV或扩大近处高度容差，也不应无条件用任意一帧覆盖历史确认。
